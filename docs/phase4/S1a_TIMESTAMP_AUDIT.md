## 2. What the audit measures

For each venue, a stratified sample (target ≥ 300 open and ≥ 300 recently resolved markets; strata: sports by sport, esports, short-term crypto, other crypto, politics, culture/other, from tags when
present, else title/slug keywords: `categorize`, a heuristic whose error rate is unmeasured):

1. **Inventory** of every time-like field on market and event objects (nested objects flattened to dotted paths; `events[].x` = the first event): name, what the *name* suggests (`classifyFieldName`), format (date-only, UTC datetime, datetime with offset, lenient `YYYY-MM-DD HH:MM:SS+00`, offset-less, epoch), precision, offset, presence by stratum.
2. **Meaning, by evidence** (never assumed): for resolved markets, each candidate field against every resolution-like field the venue provides (`closedTime`-style) and against **our own** observed resolution time (`--with-db`: the 150 most recently resolved tokens in `token_resolutions`, their markets fetched from Gamma, select-only reads); ordering of every pair of candidate fields; start-like fields against creation-like fields (a start that equals the creation time is a listing time).
3. **Placeholders**: date-only values; exact `00:00:00`, `12:00:00`, `23:59:59` UTC (and wall-clock local midnight / end of day when an offset is present); the time-of-day histogram (a field with one dominant time of day is a hidden placeholder); instants repeated across many unrelated markets (a group = one event or title family; markets of one event legitimately share a time).
4. **Disagreements**: between fields of one market (the relation tables) and, for events that exist on both venues (matched with `matchSignalToVenue`, confidence EXACT or PROBABLE only), between the venues' recommended start fields: the spread is the input to D51 (`TIMESTAMP_TOLERANCE`, proposed 15 min).
5. **Recommendation per stratum, venue and slot** by explicit, printed rules (`RECOMMEND_RULES`, `src/lib/phase4/audit.ts`). A field is recommended only if all hold; otherwise "unreliable: reject" (enough data, a rule failed) or "insufficient data":

| Rule (slot 1 = `event_start_time`, slot 2 = `market_close_time`) | Threshold (proposed; the owner may change it) |
|---|---|
| present on enough markets of the stratum | ≥ 30 |
| usable share: a datetime with time of day and zone, not a placeholder shape, over **all** markets of the stratum | ≥ 90 % |
| placeholder share of the values present | ≤ 10 % |
| no single UTC time of day on more than this share of the values | ≤ 50 % |
| slot 1: start ≤ the earliest resolution/closure reference (venue's or ours) in resolved markets (≥ 30 such markets, else *insufficient data*: meaning not established) | ≥ 99 % |
| slot 1, event-type strata (sports, esports, short-term crypto): median start→resolution | ≤ 24 h |
| slot 1: not coinciding (±60 min) with a creation-like field | ≤ 50 % of markets |
| slot 1: start ≤ a close-like field **that itself carries a real time of day** (placeholder closes are skipped) + 15 min | ≥ 95 % |
| slot 2 | the value rules only; **always flagged for human review**: a deadline's relation to resolution cannot be asserted without knowing what the venue means by it |

Why these rules exist is visible in the tests: running the first version on the synthetic world exposed that (a) a midnight-placeholder close precedes almost every kick-off, so comparing a start with it rejects a good field; and (b) a listing time passes every ordering rule unless it is compared with the creation time. Both were fixed and are pinned by tests.

Output files (`--out-dir`, default `docs/phase4/data`): `s1a_polymarket_intl.json`, `s1a_polymarket_us.json` (inventory, per-stratum evidence, recommendations), `s1a_summary.json` (also read by the S1b probe), `S1a_RESULTS.md` (generated tables); sanitised raw samples to `tests/fixtures/phase4/s1a_<venue>_{open,resolved}.json` (first ≤ 40 markets each, ≤ 380 kB, long strings truncated, images/descriptions removed).

## 4. The §3.3 rules as implemented

| Plan clause | Implementation (`src/lib/phase4/timestamps.ts`) | Tests (`tests/phase4-timestamps.test.ts`) |
|---|---|---|
| ISO-8601 with offset, converted to UTC | `parseTimestamp` (strict: `T`, `Z`/`±HH:MM`/`±HHMM`; **lenient**: space separator, short `±HH`, lowercase `z`, marked and rejected unless the audit accepted the field); calendar validation incl. leap years | parse block (offsets, fractions, lenient, invalid dates) |
| Never a date-only value, a resolution/settlement time, our `markets.end_date`, Grok's value | `validateTimestamp`: date-only / offset-less / epoch rejected; `classifyFieldName` → `RESOLUTION_LIKE`, `CREATION_LIKE`, `UPDATE_LIKE` rejected by **name** before the value is read; our end date and Grok are not inputs at all | "NEVER accepts a resolution-time field", date-only, offset-less |
| Window: evaluation time … 400 days ahead | both ends inclusive; past → `PAST` (valid for E4 via `allowPast`, see GAP_REPORT U2) | window test at ±1 ms |
| Placeholder fields rejected for a market type | `knownPlaceholderField` option (set from the audit's per-stratum verdict); optional placeholder-shaped value rejection | placeholder tests |
| (1) if present and valid; (2) only if (1) absent; else `TIMESTAMP_MISSING` | `resolveEventTime`; present-but-invalid start does **not** fall back (GAP_REPORT U1) | hierarchy block |
| (1) later than (2) by more than the tolerance → `TIMESTAMP_AMBIGUOUS` | strictly greater: exactly the tolerance is accepted | edge tests |
| Venue authority: agree within tolerance else `TIMESTAMP_VENUE_MISMATCH` | strictly greater fails; a date-only/invalid signal-venue time is recorded `NOT_COMPARABLE` and never used as the event time | edge tests |
| Journal: field name and raw value of every timestamp used | `ResolveResult.used` | "returns the source field name and the raw value" |
| §3.4 24 h / in-play / lead time | `eligibilityTimeChecks` (exact boundaries; all failures returned) | 23 h, 24 h, 24 h + 1 s, ≤ 0, `MIN_LEAD` ± 1 ms, Man U 3:30 / 4:30 examples |

`npm run phase4:mutations` breaks each of these on purpose (T1–T14, P1–P18) and checks the tests fail.

## 5. How to run

```
npm run phase4:ts-audit -- --with-db        # needs NEXT_PUBLIC_SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY (select only); omit --with-db for network only
# options: --out-dir docs/phase4/data  --fixtures-dir tests/fixtures/phase4 | --no-fixtures  --sample-open 300 --sample-resolved 300 --fetch-factor 3
#          --no-us  --us-base URL --us-markets-path /v1/markets --us-open-query 'a=b' --us-closed-query 'a=b' --us-page-size 100
```
≈ 2 requests/second: about 10 listing pages per venue plus up to 150 single-market reads with `--with-db` (≈ 3 minutes). If a stratum is printed with fewer than 30 markets (the `strata open/resolved` line) its verdict will be *insufficient data*: raise `--fetch-factor` (markets fetched = factor × sample size; the listing order is the venue's, so thin strata mean the first pages did not contain them). Prints ≤ 60 lines (Railway-safe); exit 0 even when a venue is unreachable. Commit `docs/phase4/data/s1a_*.json` and the new fixtures; the S1b probe reads `s1a_summary.json`.

## 7. Ambiguities and the cheapest test that resolves each

| Ambiguity | Cheapest test |
|---|---|
| Does Gamma's `startDate` mean listing or event start? Does `gameStartTime` exist for sports and esports only? | S1a on the international venue: `coincidesWithCreationShare`, `medianStartToResolutionHours` per stratum |
| Is `endDate` a placeholder (midnight) for sports? Do crypto "up or down" markets carry real deadlines with time of day? | S1a inventory: top times of day and placeholder share per stratum |
| Which resolution-like fields exist on the US venue and how are they named? | S1a on the US venue after the endpoint check (§3) |
| Does a start time ever move (postponement)? | Two S1a runs a day apart on the same open markets, comparing the recommended field (a 5-line diff of two `s1a_*` samples); the plan's re-fetch at authorization is the production answer |
| Are the venues' event times for the same match equal? | `venueAgreement` in `s1a_summary.json` (matched events per stratum are counted: read a stratum with fewer than ~30 pairs as indicative only) |
| Is the public US market-data API really keyless and are automated reads permitted by its terms? | Read the terms at docs.polymarket.us before the first run; the first unauthenticated GET shows the key question |
| Do `lenient` formats (space separator, `+00`) occur, and may they be accepted? | `formats` per field in the inventory; `lenientFormatShare` in the recommendation evidence; accept per field only when 100 % lenient *and* consistent |
| Time zone of date-only values (`endDateIso`) | Irrelevant to the rules (date-only is never used) but needed to read the proxy; compare `endDateIso` with the UTC date of `endDate` where both exist |
